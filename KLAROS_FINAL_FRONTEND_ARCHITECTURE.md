# Klaros AI — Final Frontend Architecture

Covers item R (UX evolution) and item M (website builder, frontend-facing half — backend model in KLAROS_FINAL_DOMAIN_MODEL.md).

## Verified current state

Next.js 16 App Router, React 18.3.1, TypeScript, Tailwind. File-based routing under `frontend/app/`, no explicit route-config. 57+ pages. Single centralized `frontend/lib/api.ts` (3,835 lines, flat, typed-per-endpoint, no per-domain split). Retry logic (`withRetry`, exponential backoff) used throughout the dashboard's 16-endpoint fan-out. Auth: `sessionStorage`-held tokens, silent-refresh-on-401 with in-flight-request de-duplication. No global fetch interceptor — every `lib/api.ts` function takes `token` explicitly. Custom in-house toast system (`ToastProvider`, no external library), replacing old inline "notice" banners. CRUD pattern: plain `useState`-controlled forms, no form library, native HTML validation, `Modal`-based create flows, separate `[id]` detail routes. Navigation source-of-truth: `AppShell.tsx`'s `NAV_SECTIONS`. No frontend test framework, no test files, anywhere.

## UX evolution: Describe business → Answer questions → Review Blueprint → Review recommendations → Connect integrations → Configure agents → Configure workflows → Build website → Review launch readiness → Launch → Operate

| Stage | New or reused page | Reuse detail |
|---|---|---|
| Describe business | New `/discovery` | New page, but reuses `Modal`/`Field`/`Input`/`Button` primitives and the existing controlled-form pattern — no new form library introduced just for this |
| Answer questions | `/discovery` (same page, conversational turn UI) | New, adaptive-question rendering component |
| Review Blueprint | New `/blueprint` | Renders `BlueprintSection`s; section-edit forms reuse the same plain-`useState` CRUD pattern as every existing domain page (e.g. `/customers`) |
| Review recommendations | New `/recommendations` | List/accept/dismiss pattern mirrors existing list pages (search + table + row actions), same `EmptyState`/`Skeleton` components |
| Connect integrations | **Reused, extended**: `/settings/integrations` | Existing 872-line page already has the real per-provider connect/disconnect pattern (Stripe/QuickBooks/Google Calendar) and the `PLANNED_OAUTH_PROVIDERS` NOT_IMPLEMENTED honesty pattern — extended with the new catalog-derived status taxonomy (KLAROS_FINAL_INTEGRATION_MODEL.md), not rebuilt |
| Configure agents | New `/agents` | New page; agent tool-selection UI is the one place a slightly richer form control (multi-select with search) is warranted — still no full form-library adoption required for this alone |
| Configure workflows | New `/workflows` (distinct from existing `/automations`) | **Deliberately distinct from `/automations`**: `/automations` remains the existing deterministic trigger/condition/action UI (927 lines, fully built out, unchanged); `/workflows` is where a Blueprint-derived, potentially-agent-involving `Workflow`/`WorkflowVersion` spec (KLAROS_FINAL_DOMAIN_MODEL.md) is authored, which *compiles into* either an `Automation` or a Temporal workflow. Two pages because they edit two different abstraction levels — `/workflows` is not a competing engine, it is the spec-authoring UI whose output lands in the existing `/automations`-managed engine when the shape is a simple trigger-chain. |
| Build website | New `/website` | Fixed-component-registry editor (drag/select from registry, fill content slots) + `/website/preview` (renders via the **same** component registry used in production — no separate "preview renderer" to keep in sync) |
| Review launch readiness | New `/launch-readiness` (or a tab on `/blueprint`) | Aggregates Blueprint completion criteria (KLAROS_FINAL_BUSINESS_BLUEPRINT.md), required integrations connected, at least one agent/workflow configured if required by the vertical, website published-or-explicitly-skipped |
| Launch | Action on `/launch-readiness` | Publishes `WebsiteVersion` (if applicable), activates `BusinessBlueprint`, transitions org out of "setup" state |
| Operate | **Fully reused**: existing dashboard + all 57 operational pages | No new "second dashboard" — the existing "Owner Cockpit" dashboard (`/dashboard`) remains the single operating home; new sections (Agents summary, Blueprint status) are added as additional cards in the existing `Promise.allSettled` fan-out pattern, not a parallel dashboard |

**Explicit avoidance of a second dashboard**: the existing dashboard already aggregates AI kill-switch, autonomy/AI Control Center, automations summary, and CRM/finance/marketing/retention metrics into one page via a proven, retry-hardened fan-out pattern. New Agent/Blueprint/Recommendation summaries are added as more cards in that same pattern, reusing `StatCard` and the existing skeleton/empty-state components — not a rebuild.

## Website Builder (item M) — frontend-facing architecture

**Hard constraint (upheld throughout):** the LLM never generates arbitrary production code. Pipeline: `BusinessBlueprint` → deterministic Website Requirements (rule-derived from Blueprint sections, e.g. "has Products/Services section with >0 items → include a Services page") → Site/Page/Component Specification (JSON referencing a **fixed component registry** — Hero, FeatureGrid, TestimonialSection, ContactForm, ServiceList, etc. — never free-form HTML/JS) → Content Specification (the LLM's only job: fill declared text slots — headline, body copy, CTA text — within a component's schema, never structure or markup) → Preview (renders the spec through the identical component-registry renderer used in production, so "what you see in preview is exactly what publishes" is structurally true, not a promise) → Validation (schema + required-field + broken-link checks) → Human Approval (`PublishRequest`, reusing the existing `ApprovalRequest` approve/reject UI and backend flow — no new approval UI built) → Publish on an isolated website-runtime origin (separate from the app's own origin, limiting blast radius of any future website-layer issue).

**Forms**: a generated site's forms submit only to the allowlisted public endpoints (`public_leads`, new `public_appointment-requests`) — the component spec for a form component can select *which* allowlisted target it posts to, never an arbitrary URL field.

**Models**: `Website`/`WebsiteVersion`/`WebsitePage`/`WebsiteSection`/`WebsiteFormBinding` (KLAROS_FINAL_DOMAIN_MODEL.md). Theme = a bounded token set (colors/fonts/spacing scale) applied to the fixed registry's components, not free CSS. SEO = per-page structured metadata fields on `WebsitePage`, not a free-text injection point. Domain mapping = existing pattern extended (the app already handles multi-tenant routing at the API layer; the website-runtime origin adds a tenant-to-custom-domain mapping table, new but structurally simple). Versioning/rollback: publishing a prior `WebsiteVersion` **is** the rollback mechanism (KLAROS_FINAL_DOMAIN_MODEL.md) — no separate rollback tooling needed.

## Decisions carried forward, now made

- **Form library**: no new dependency adopted platform-wide. The existing plain-`useState`-per-field pattern is kept for all pages that already use it and for most new pages (Discovery answers, Blueprint section edits, Recommendation actions). The one exception — Agent tool-permission multi-select — uses a small, purpose-built component, not a new library dependency, keeping the "no state-management/form-library dependency" characteristic of the current frontend intact rather than introducing react-hook-form for one screen.
- **Frontend testing must start at Phase 0**, not be deferred — see KLAROS_FINAL_TESTING_ARCHITECTURE.md for the concrete framework decision (Vitest + React Testing Library + Playwright) and why it's decided now rather than left open, closing the "UNKNOWN — REQUIRES DECISION" flag several source documents carried.
