## Data model validation — the explicit non-reuse rule

**`Vendor`/`VendorBill` must not be reused for `Supplier`/`Product`/`SKU`.** Verified: `Vendor` has exactly 4 business columns (`name`, `email`, `phone`, `status`) and `VendorBill` has 5 (`vendor_id`, `job_id`, `amount`, `due_date`, `status`, `external_reference`) — no product, SKU, price, or catalog concept anywhere in either (`finance.py:236-261`, direct read confirmed). This is the largest new relational domain in the entire plan precisely because — unlike Medical Tourism, which extends an existing (if incomplete) `Referral` concept — dropshipping has **zero** existing foundation to extend from; `Product`/`SKU`/`Order`/`OrderLine`/`Supplier`/`InventorySnapshot`/`SupplierOrder`/`Shipment`/`OrderReturn` are all genuinely net-new tables, confirmed by an exhaustive grep across all 18 existing model files finding zero `class (Product|SKU|Order|Inventory|Cart)` matches.

`Cart` is deliberately not a backend table (ephemeral client-side/session state only, becoming an `Order` row at checkout submission) — matches the existing codebase's pattern of having no backend "draft" concept anywhere else either.

## What existing code required zero change

`Customer`, `Invoice`, `Payment`, `CustomerService`, Finance services, `marketplace_adapters.py`'s generic-webhook pattern (reused conceptually, not modified), RBAC/permission chain, `ToolRegistry`, `AuditLog` — all reused as-is.
