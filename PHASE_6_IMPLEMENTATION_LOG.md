## 4. Crash recovery architecture

```
AgentReasoningService.start() / resume_after_approval()
    -> claims/renews the execution's lease as this process's own worker_id
       (execution_owner_id, lease_expires_at = now + 5min, heartbeat_at)
    -> _run_loop(): heartbeat-renews the SAME lease at the top of every
       iteration (conditional UPDATE ... WHERE execution_owner_id = self —
       never extends another owner's lease)

AgentRecoveryService.sweep_once()  [an EventWorker on_tick hook]
    -> find AgentExecution rows: status=RUNNING AND
       (lease_expires_at IS NULL OR lease_expires_at < now())
    -> for each candidate: ONE atomic conditional UPDATE
           SET execution_owner_id=<new>, lease_expires_at=<now+5min>,
               recovery_attempt_count = recovery_attempt_count + 1
           WHERE id=<id> AND status='RUNNING'
             AND (lease_expires_at IS NULL OR lease_expires_at < now())
       -- checked via rowcount == 1 (the exact CAS pattern
          ApprovalExecutionService already uses for execution_status)
    -> if recovery_attempt_count > MAX_RECOVERY_ATTEMPTS (5): halt
       permanently (RECOVERY_ATTEMPTS_EXHAUSTED) — poison-execution bound
    -> if mode == SINGLE_ACTION: halt permanently
       (RECOVERY_UNSAFE_SINGLE_ACTION) — never resumed, see §8
    -> if mode == REASONING: AgentReasoningService.resume_recovered()
       -> _reconcile_interrupted_step(): the most recent AgentExecutionStep
          row, if its completed_at IS NULL (written by
          _attempt_tool_call's initial mark_pending=True write, never
          updated with an outcome), is marked FAILED/interrupted_by_crash
          — that step_number is NEVER re-attempted
       -> _run_loop() resumes exactly as any other continuation would —
          same code path, not a second implementation
```

A single atomic conditional `UPDATE` is the entire claim mechanism — no explicit `SELECT ... FOR UPDATE` or Postgres advisory lock was added on top of it. Reasoning: under Postgres's row-level locking, two concurrent `UPDATE`s targeting the same row's `WHERE` clause cannot both succeed — the second transaction blocks until the first commits, then re-evaluates its `WHERE` clause against the now-changed row and, finding it no longer matches (`status` unchanged but `lease_expires_at`/`execution_owner_id` already rewritten... actually `status` stays `RUNNING` through a successful claim, so the actual exclusion is that the row's `lease_expires_at` is now far in the future), affects zero rows. This is the exact same "conditional UPDATE, checked via `rowcount`" pattern `ApprovalExecutionService.execute_approved`'s own `execution_status` CAS already used and proved correct in Phase 4 — reused here rather than inventing a second concurrency primitive. Verified for real (not just argued) in `test_postgres_agent_recovery.py::test_double_recovery_race_exactly_one_worker_claims`.

## 5. Lease/ownership design

- **Fields** (additive, on `AgentExecution`, migration `0047`): `execution_owner_id` (Uuid, nullable), `lease_expires_at` (DateTime(tz), nullable), `heartbeat_at` (DateTime(tz), nullable), `recovery_attempt_count` (Integer, default 0).
- **Tenant scope**: every lease operation (claim, renew, sweep query) is a query/update on `AgentExecution`, which is already `TenantScopedMixin`-scoped and RLS-audit-mode-instrumented (Phase 4's table); the sweep additionally accepts an optional `tenant_id` filter (used by tests and by any future tenant-scoped admin trigger, mirroring `AutomationService.check_and_dispatch_scheduled`'s own `tenant_id` parameter).
- **Atomic acquisition**: single conditional `UPDATE`, `rowcount`-checked (§4).
- **Renewable**: `AgentReasoningService._renew_lease`, a conditional `UPDATE ... WHERE execution_owner_id = self._worker_id`, called once per loop iteration.
- **Safely expired**: purely by comparison against `now()` in every query that matters (claim, and the safety-matrix "fresh execution is not a candidate" tests) — no separate expiry sweep/cron needed.
- **Never an in-memory lock**: confirmed by construction — `AgentRecoveryService`/`AgentReasoningService` hold no Python-level lock object anywhere; every ownership decision is a database row.

## 6. Scheduler design

`AgentTriggerService.check_and_dispatch_scheduled` (`backend/app/services/agent_trigger_service.py`), wired as an `EventWorker` `on_tick` hook (both in `app/events/worker.py::_standalone_main` and `app/main.py`'s in-process dev-fallback worker — the same two call sites the Automation Engine's own scheduler hook lives in). No cron syntax: reuses `automation_schedule.check_due`/`validate_schedule_config` verbatim — `{"frequency": "DAILY"|"WEEKLY", "time": "HH:MM", "weekdays": [...]}`, evaluated against `Organization.timezone` via `zoneinfo`. Missed-schedule policy: **skip, never catch-up** — `check_due` only ever asks "is today's tenant-local occurrence due right now," never "how many were missed"; a late tick still fires that day's occurrence exactly once (proven by `test_missed_schedule_does_not_catch_up_multiple_days`), a worker outage never produces a burst of backfilled executions. A due-but-non-ACTIVE Agent is explicitly recorded as `agent.trigger.scheduled.skipped` (audited, `AgentExecution` never created) — never silently ignored, never a doomed `RUNNING` row. A disabled schedule (`triggers.schedule.enabled=false`) is filtered out before "due" is even evaluated — zero executions, by construction.

## 7. Event-trigger design

`app/events/agent_trigger_handlers.py::register_agent_trigger_handlers`, registered once inside `get_wired_event_bus()` (`app/api/tool_deps.py` — the one bootstrap root shared by every runtime path: HTTP requests, the in-process dev worker, the standalone worker OS process, and the test suite's `event_bus` fixture indirectly via any test that constructs its own bus the same way). One generic dispatcher subscribed to every `EventType`, structured directly on `automation_handlers.py`'s proven pattern. Deterministic filtering only (`_matches`: plain structural equality over `event.payload`, `event_type` match required first) — the LLM never sees an event and never decides whether it should trigger an Agent; it only starts reasoning after the deterministic gate has already decided to begin. Event payload is treated as fully untrusted: the goal handed to `AgentReasoningService.start()` is always the operator-authored static `triggers.event.goal` string plus a small, fixed metadata note (`event_type`/`entity_type`/`entity_id` only) — raw payload values are never interpolated into the prompt (see `_build_goal`), and `conditions` matching is the only place the payload is read at all, producing a boolean, never text. Proven directly by `test_prompt_injection_in_event_payload_never_reaches_the_goal`, which asserts a crafted "ignore instructions / call secret_tool / change tenant" payload string never appears in what the model actually saw, and that `event.tenant_id` (never the payload's own claimed `"tenant_id"` field) is what the resulting execution is scoped to.

## 8. Idempotency model

One mechanism, reused everywhere: `AgentExecution.idempotency_key`'s real DB unique constraint on `(tenant_id, agent_id, idempotency_key)` (Phase 4 schema, unchanged). Deterministic keys, never `uuid4()`:
- Scheduled: `f"schedule:{agent.id}:{due.occurrence_date.isoformat()}"` — a retried/duplicated tick for the same tenant-local calendar date resolves to the same key.
- Event: `f"event:{event.id}:{agent.id}"` — a redelivered event resolves to the same key for the same (event, agent) pair; a different Agent subscribed to the same event still gets its own row (dedup is per (event, agent), never global).

## 9. Execution guarantees (exactly-once vs. at-least-once, per scenario)

| Scenario | Internal state transition | External tool side effect |
|---|---|---|
| Crash before tool execution (decision persisted, step written pending) | Exactly-once: that step is marked `interrupted_by_crash`/FAILED on recovery, the tool call for that step_number is never attempted again. | Never fired — nothing to guarantee. |
| Crash during tool execution (call in flight) | Exactly-once at the runtime-state level: recovery never re-issues that exact call. | **At-least-once, honestly**: if the tool's own side effect had already taken effect before the crash, this runtime has no way to know and does not claim otherwise — the step is marked interrupted, its result is lost from the reasoning trace, and the loop moves on to a fresh decision. Tools are not currently passed an idempotency identity of their own (no tool contract in this registry accepts one — verified via the same registry grep as §2/§12), so this is a real, disclosed limitation, not a solved problem. |
| Crash after tool execution, before result committed | Same as above — the step row exists but was never finalized; treated identically (interrupted, never re-run). | At-least-once (the call already completed). |
| Crash after step committed, before next reasoning call | Exactly-once: `_run_loop` resumes cleanly from `step_count`, full history intact, no step lost or re-attempted. | Not applicable — no tool call was in flight. |
| Crash during the LLM call itself | Exactly-once: no `AgentDecision` was ever produced or acted on; resume simply asks the model again for the same step_number. | Not applicable. |
| Crash during approval resume | Not this phase's concern by design — `WAITING_APPROVAL` is never a recovery-sweep candidate (filtered out by `status == RUNNING`); `ApprovalExecutionService`'s own existing compare-and-swap (`execution_status` CAS) already guarantees a repeated resume callback is a no-op. | Governed by the existing Phase 4 CAS, unchanged. |
| Scheduled/event trigger delivered twice | Exactly-once `AgentExecution` row — proven against real Postgres under true concurrent duplicate requests (`test_postgres_agent_trigger_concurrency.py`). | The Agent's own tool calls, once, for that one execution — same guarantees as the row above. |

## 10. Security model

- **Tenant**: every recovery/trigger query is tenant-scoped (`AgentExecution.tenant_id`, `Agent.tenant_id`, `Event.tenant_id`); `test_tenant_isolation_event_cannot_trigger_another_tenants_agent` proves a Tenant A event never even queries, let alone triggers, a Tenant B agent.
- **RBAC/actor**: triggered executions use `triggered_by=None` (no human actor) with `trigger_source` (`SCHEDULED`/`EVENT`) as the sole "who/what" signal on the `AgentExecution` row — exactly mirroring `AutomationExecution.triggered_by=None` for `check_and_dispatch_scheduled`'s own dispatches (the existing, already-established precedent for "no human initiated this," re-confirmed via forensic research rather than invented). Recovery/trigger audit rows use `ActorType.SYSTEM` (an existing enum value, previously unused for automated dispatch — now given its first real writer in this codebase).
- **Autonomy/tool-permission/approval**: entirely unchanged — a triggered execution goes through the exact same `AgentReasoningService.start()` → `ToolRegistry.execute()` pipeline as a manual one; nothing in the trigger path can widen what an Agent's autonomy tier or tool-permission snapshot already allows.
- **Kill switch**: no special-case code anywhere in the recovery/trigger path — `ToolRegistry.execute()`'s existing `ai_paused` check re-runs fresh on every governed call, proven under recovery specifically by `test_kill_switch_blocks_next_tool_call_after_recovery`.
- **Version immutability / permission-snapshot immutability under recovery**: proven by `test_version_immutability_preserved_during_recovery` (a recovered execution's `agent_version_id` is never rewritten to a newer published version, and its next tool call is cleanly rejected — not silently permitted under stale authority nor silently upgraded) and `test_live_permission_revocation_does_not_affect_recovered_execution` (a live grant revoked before recovery does not affect a recovered execution still authorized by its immutable snapshot).
- **Event payload untrusted**: §7.
- **Rate/concurrency limits shared**: scheduled/event-triggered executions call the exact same `AgentExecutionService._enforce_rate_and_concurrency` helper manual executions use — no bypass path, no separate ceiling.

1. **Real concurrency bug, found via a deliberate forced-concurrency repro against real Postgres while writing this phase's mandatory trigger-dispatch concurrency tests (exactly the kind of bug this phase's instructions anticipated).** `AgentExecutionService._create_execution_row` (Phase 4) and `AgentReasoningService.start` (Phase 5) both used a check-then-insert idempotency pattern (`_find_by_idempotency_key` pre-check, then a plain `session.add()`/`commit()`) with **no `IntegrityError` handling on the insert** — unlike `AutomationService.start_execution`'s own, already-correct pattern for the identical race. Under genuine concurrent duplicate-idempotency-key requests (proven with 5 truly concurrent `asyncio.gather` calls against real Postgres — a naive 2-way `asyncio.gather` on fast local-socket Postgres calls was NOT sufficient to force the race, which is itself a documented finding: cooperative-scheduling races need either enough concurrent contenders or explicit interleaving to reproduce reliably), the second-and-later callers raised a raw, unhandled `asyncpg.exceptions.UniqueViolationError`/SQLAlchemy `IntegrityError` instead of the intended `DuplicateExecutionRequestError` — exactly the failure mode Phase 6's "duplicate scheduler delivery / duplicate event delivery must resolve to one logical execution" requirement exists to prevent, and squarely hit by this phase's own new concurrent trigger-dispatch paths (two overlapping scheduler ticks, two event redeliveries). **Fixed** in both call sites: the insert's `commit()` is now wrapped in `try/except IntegrityError`, rolling back and re-raising as `DuplicateExecutionRequestError` pointing at whichever row actually won — the exact same shape `AutomationService.start_execution` already used. Proven fixed by `test_postgres_agent_trigger_concurrency.py::test_concurrent_duplicate_idempotency_key_never_raises_raw_integrity_error` (5-way genuine race, real Postgres).
2. **Test-authoring finding, not a product bug (documented for completeness, same spirit as Phase 4/5's own caught test-authoring bugs):** the first draft of `test_version_immutability_preserved_during_recovery` assumed a recovered execution pinned to an old (now-superseded) `AgentVersion` should still successfully complete a further tool call after a newer version was published. Against real Phase 4 governance (`ToolRegistry._check_agent_tool_permission`'s `agent.current_version_id != version.id` check, pre-existing and correct), this is actually always rejected — for ANY in-flight execution, not something Phase 6 introduces. Corrected the test's expectation rather than the product: the execution's `agent_version_id` must never silently switch to the new version (proven), and its next tool call is cleanly `TOOL_GOVERNANCE_REJECTED` rather than either silently permitted under stale authority or silently upgraded — which is the actually-correct, stronger form of "version immutability."

## 14. Known limitations

- **SINGLE_ACTION-mode executions are never automatically resumed after a crash** — only ever safely halted (`RECOVERY_UNSAFE_SINGLE_ACTION`). Phase 4's schema has no step-level durability boundary (unlike Phase 5's `AgentExecutionStep`), so there is no way to determine whether the tool already ran; rather than guess, this is a conservative, honestly-documented gap. A human must inspect and manually re-issue such a request. A future phase could add step-level durability to the single-action path if this proves to be a real operational pain point.
- **External tool side effects that fire just before a crash are honestly at-least-once, not exactly-once** — see §9's table. No tool in the current registry accepts an idempotency identity of its own (verified via grep), so this runtime cannot pass one through even where it would help; this is a pre-existing property of the tool contract (`app/tools/base.py::Tool`), not something Phase 6 could close without a broader tool-contract change, which is out of this phase's scope.
- **The lease-duration constant (5 minutes) is a judgment call, not empirically tuned** against real production LLM-call latencies — reasonable given `max_tool_chain_depth` is typically small (single digits) and each step makes at most 2 LLM calls (one retry), but genuinely long chains against a slow AI provider could in principle need a longer lease; the heartbeat renewal at every loop iteration mitigates this for any chain that is actually still making progress.
- **`recovery_attempt_count` is incremented on every successful claim**, including ones where recovery ultimately succeeds — so a healthy execution that happens to cross the lease-expiration boundary during unusually slow (but real) progress could accumulate attempts toward the bound over a long enough operational lifetime. `MAX_RECOVERY_ATTEMPTS = 5` was chosen as a reasonable, small, explicit bound per this phase's instructions, not derived from a production incident (none exists yet).
- **Trigger-management remains config-via-existing-field, not a dedicated API** — `AgentVersion.triggers` is set through the existing `POST /agents/{id}/versions` request body (already accepted that field since Phase 4); no new `/agents/{id}/schedules` or `/agents/{id}/event-triggers` CRUD endpoints were added, since the existing endpoint already covers create/version/publish and no architecture document requires a separate surface. An operator wanting to "disable a schedule" today publishes a new version with `triggers.schedule.enabled=false` — consistent with how `AgentVersion`'s other executable fields (tool-permission snapshot, `max_tool_chain_depth`, etc.) are already only changeable via a new version, never an in-place PATCH.
- **No UI was built** — this phase, like every prior backend phase, is backend-only.
- **The full exhaustive test matrices named in this phase's prompt (DST transitions, scheduler-restart/worker-restart simulations as literal process kills, every cell of the Schedule/Event Security Matrices) were not all individually written as separate named tests** — the safety-relevant *properties* they test (stale detection, atomic claim, poison-execution bound, tenant isolation, kill-switch, version/permission immutability, deterministic filtering, payload distrust, duplicate-delivery dedup, disabled/paused/archived skip, missed-schedule skip-not-catchup, timezone correctness) are each covered by at least one real test against real Postgres where concurrency matters, but this is a narrower, higher-signal set (42 new tests) rather than an exhaustive combinatorial matrix. Flagged honestly rather than claiming full matrix coverage that wasn't actually written.
