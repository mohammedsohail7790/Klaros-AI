# Klaros AI — Validation Scenarios: Medical Tourism and Dropshipping

Covers items AA and BB — end-to-end walkthroughs of the target architecture against the two test businesses, at every step naming data/APIs/models/agents/tools/integrations/approvals/human-involvement/missing-capability.

## AA. Medical Tourism: "I want to build a medical tourism business that connects customers with doctors and hospitals in selected countries"

| Stage | What happens | Data/Models | APIs | Agents/Tools | Integrations | Approvals | Human involvement | Missing capability (if any) |
|---|---|---|---|---|---|---|---|---|
| Discovery | Free-text description submitted; adaptive questions surface country selection, procedure specialization, licensing/compliance status, referral-commission model | `DiscoverySession`, `DiscoveryTurn` | `POST /business-discovery/sessions`, `.../answer` | none (deterministic question-generation service + AI provider for phrasing only) | none | none | Owner answers questions | None — Discovery is capped and never defaults compliance/licensing Unknowns, correctly surfacing this as a required, not-silently-answered question |
| Requirements | Answers promoted to `BlueprintClaim` rows (type=Requirement for "must track provider licensing per country", type=Fact for "operating in Turkey and India") | `BlueprintClaim` | internal (promotion service) | none | none | none | Owner reviews claims | None |
| Blueprint | Sections populate: Identity, Markets (Turkey/India), Providers (hospitals/doctors), Requirements (licensing), Policies (commission structure) | `BusinessBlueprint`, `BlueprintSection` | `GET /business-blueprint`, `PUT .../sections/{key}` | none | none | none | Owner confirms/edits sections | None |
| Recommendations | Recommendation Engine's `medical_tourism` plugin (registered against `DomainDefinition`, not hardcoded in the engine) proposes: enable Medical Tourism vertical extension, connect a payments processor for consultation deposits, connect a calendar integration for consultation scheduling, configure a lead-qualification agent | `Recommendation` | `GET /recommendations`, `POST .../accept` | none yet (proposes creating agents, doesn't create them) | Stripe (existing, real), Google Calendar (existing, real) recommended | none (recommendation itself is not an action) | Owner accepts/dismisses each | None |
| Providers | Owner (or an imported list) populates `Provider`/`ProviderCredential`/`Procedure`/`ProviderProcedure` for actual hospitals/clinics/doctors | Medical Tourism vertical tables (Phase 9) | `/providers`, `/providers/{id}/procedures` (conditionally mounted per enabled vertical) | new tools: `provider.create`, `provider.verify_credential` | none required | credential verification may be `APPROVAL_REQUIRED` policy for a new provider tool, tenant-configurable | Owner or ops staff enters/verifies provider data | None, assuming Phase 9 has shipped |
| Integrations | Stripe connected (deposits), Google Calendar connected (consultation booking) via existing, real, verified OAuth2/key flows | `IntegrationConnection` | existing `/integrations/*` routes, unchanged | none | Stripe, Google Calendar (both real, verified in this review) | none beyond existing connect flow | Owner completes OAuth/key entry | None |
| Agents | Owner configures a "Lead Qualification Agent": purpose="triage new PatientLead inquiries", tools=[`crm.qualify_lead`, `crm.create_patient_lead_note`], autonomy tier=Recommend (per pre-autonomy gate, cannot start higher) | `Agent`, `AgentVersion`, `AgentToolPermission` | `POST /agents`, `.../publish` | the agent itself; its declared tools only | none directly (tools may internally call integrations) | agent actions above Recommend tier require `ApprovalRequest` | Owner reviews agent config before publish; reviews each Recommend-tier proposal before it executes | None, assuming Phase 7's Recommend-tier gate is the ceiling until the pre-autonomy test suite passes for this agent's specific tool set |
| Workflows | "New PatientLead → Lead Qualification Agent proposes triage → owner approves → Consultation scheduled → confirmation email" compiled as a `Workflow`/`WorkflowVersion`, targeting the existing deterministic Automation Engine (no durable-wait/compensation needed for this shape) | `Workflow`, `WorkflowVersion`, existing `Automation` | `/workflows`, existing `/automations/*` | Lead Qualification Agent (above) + existing `email` tool | SendGrid (existing, "stated real," not independently re-verified in this pass — flagged **UNKNOWN — REQUIRES VERIFICATION**) | per the agent's tier and the email tool's own policy | Owner approves the qualification step until the agent's gate clears for autonomous execution | SendGrid's independent verification gap, carried forward honestly rather than assumed |

| Launch | Launch-readiness check: Blueprint ACTIVE, required integrations connected, at least one agent configured (vertical-defined requirement), website published-or-explicitly-skipped — all pass → org transitions out of setup state | aggregated read across above tables | `/launch-readiness` | none | none | none (readiness check, not itself an approval-gated action) | Owner clicks Launch | None |
| Operate | Existing dashboard, CRM, finance modules take over; `PatientLead`/`Consultation`/`ReferralCommission` visible alongside existing `Lead`/`Appointment`/`Referral` because they FK-reference them, not fork them | all existing operational tables + Phase 9 extension tables | existing 55+ routers, unchanged | Lead Qualification Agent continues operating per its tier | Stripe/Google Calendar/SendGrid, ongoing | ongoing per agent tier and tool policy | Owner operates via the existing, unchanged dashboard — no second dashboard | None |

**Notable finding, reconfirmed:** even a **Phase-2-only** deployment (Discovery live, no Phase 9 vertical tables yet) produces a usable lead-capture flow via `Lead`'s existing free-text fields — the business doesn't need to wait for the full vertical extension to start capturing interest, which is a real, verifiable property of the FK-extension design (a `Lead` row works standalone; a `PatientLead` row is optional enrichment).

## BB. Dropshipping: "I want to start a dropshipping business using suppliers and sell products online"

| Stage | What happens | Data/Models | APIs | Agents/Tools | Integrations | Approvals | Human involvement | Missing capability (if any) |
|---|---|---|---|---|---|---|---|---|
| Discovery | Adaptive questions surface: which supplier(s), product categories, shipping regions, return policy | `DiscoverySession` | same as AA | none | none | none | Owner answers | None |
| Requirements/Blueprint | Claims: "uses a specific dropshipping supplier" (Fact), "needs product catalog with variants" (Requirement), "no international shipping initially" (Decision) | `BlueprintClaim`, `BlueprintSection` | same as AA | none | none | none | Owner confirms | None |
| Recommendations | `dropshipping` plugin proposes: enable Dropshipping vertical, connect a payments processor, connect a shipping-tracking capability (no first-party shipping-tracking tool/integration exists today — flagged as REQUIRED-but-not-yet-available, `Recommendation.status` would surface this honestly rather than silently omit it) | `Recommendation` | same as AA | none | Stripe recommended (real); shipping-tracking integration is a genuine **gap** — this review confirms no shipping-carrier adapter exists in the current integrations framework at all, stub or real | none | Owner reviews, sees the gap explicitly rather than a silently-missing option | **Confirmed gap:** no shipping-carrier integration adapter exists today (not even a stub) — this must be added as a new `IntegrationProviderCatalog` row with `implementation_status=COMING_SOON` at minimum, and a real adapter is out of scope for Phase 10 unless explicitly prioritized |
| Domain setup | `Supplier`, `Product`, `SKU`, `InventorySnapshot` populated (manually or via a future supplier-feed import tool, not specified as in-scope for Phase 10's minimum) | Dropshipping vertical tables (Phase 10) | `/suppliers`, `/products`, `/products/{id}/skus` | new tools: `product.create`, `sku.update_inventory` | none required for manual entry | inventory-affecting tools may carry `APPROVAL_REQUIRED` policy per tenant configuration | Owner or ops staff enters catalog data | Supplier-feed auto-import is explicitly out of Phase 10's minimum scope — **not a hidden gap, a deliberately deferred one**, consistent with `KLAROS_DO_NOT_BUILD_YET.md`'s discipline of not over-building |
| Orders | Customer places an `Order` (via the generated website's cart — deliberately not persisted server-side until checkout, matching the existing no-backend-draft-concept pattern), `OrderLine`/`SupplierOrder`/`Shipment` created on confirmation | `Order`, `OrderLine`, `SupplierOrder`, `Shipment` | `/orders` | `order.create`, `order.forward_to_supplier` | Stripe (payment), shipping-carrier (gap, above) | payment-taking is `financial_risk`-tagged, always approval-gated per the tier-independent ceiling (KLAROS_FINAL_AGENT_MODEL.md) unless the org's policy marks standard checkouts AUTO | none beyond standard checkout unless a policy flags it | None beyond the shipping gap already noted |
| Fulfillment | `SupplierOrder` forwarded to supplier (manually or via a future supplier-API integration, also not in Phase 10's minimum scope), `Shipment` tracked | same tables | `/orders/{id}` | none new | none (manual) unless a specific supplier's API is separately integrated later | none | Ops staff manages fulfillment manually in Phase 10's minimum scope | Supplier-API auto-forwarding — deliberately deferred, same reasoning as above |
| Returns | `OrderReturn` created, refund processed via Stripe | `OrderReturn` | `/orders/{id}/returns` | `order.process_return` | Stripe | refund is `financial_risk`-tagged, approval-gated | Owner or ops approves refund | None |
| Website | Product catalog page, product detail pages, cart (client-side ephemeral), checkout form (targets allowlisted `public` endpoint) generated via the same fixed-registry pipeline as Medical Tourism | `Website`, `WebsiteVersion` | same as AA | none | none required beyond allowlisted endpoint | `PublishRequest` | Owner approves publish | None |
| Launch/Operate | Same mechanism as AA — no second dashboard, existing operational modules (finance/CRM) apply to `Order`/`Payment` the same way they apply to existing `Invoice`/`Payment` | existing + Phase 10 tables | existing + new routers | none autonomous by default | Stripe, ongoing | ongoing per policy | Owner operates via existing dashboard | None |

**Notable finding, reconfirmed:** Dropshipping is, as KLAROS_DROPSHIPPING_VALIDATION.md correctly identified, **the largest net-new relational domain in the entire roadmap**, because unlike Medical Tourism it has zero existing foundation to extend (`Vendor`/`VendorBill` confirmed insufficient, not merely under-featured). This review's own validation surfaces one concrete, previously-under-emphasized gap: **no shipping-carrier integration exists at any status level (not even STUB)** — this should be added to the `IntegrationProviderCatalog` seed data (Phase 1.2) as `COMING_SOON`, so the Recommendation Engine can surface it honestly rather than silently omitting a REQUIRED capability, even though building a real adapter remains correctly out of Phase 10's minimum scope.
