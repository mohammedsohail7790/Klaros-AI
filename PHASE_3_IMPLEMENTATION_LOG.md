## Recommendation model — reconciliation decision

`KLAROS_FINAL_DOMAIN_MODEL.md` and `KLAROS_INTEGRATION_MARKETPLACE_SPEC.md` describe overlapping but not identical `Recommendation` shapes, and no code precedent existed before this phase. `KLAROS_FINAL_TESTING_ARCHITECTURE.md` names the authoritative 8 required fields: **WHY / WHAT / DEPENDENCIES / COST / REQUIRED-OR-OPTIONAL / ALTERNATIVES / CONFIDENCE / SOURCE**. This implementation built `app/models/recommendation.py` around that 8-field contract exactly (`why`, `what`, `dependencies`, `cost_estimate`, `required`, `alternatives`, `confidence`, `source`), plus implementation-judgment additions mirroring `BlueprintClaim`'s own precedent: `blueprint_id`/`blueprint_version` (evidence + version binding), `based_on` (structured evidence list, not prose), `type`/`capability_key`/`provider_key`/`provider_implementation_status`/`tool_name` (what is actually being recommended), `source_vertical_key`, and lifecycle/decision columns (`status`, `decided_by`, `decided_at`, `rejection_reason`).

Lifecycle chosen: **`PROPOSED` / `ACCEPTED` / `REJECTED` / `SUPERSEDED`** — not the Domain Model doc's `PROPOSED/ACCEPTED/DISMISSED`. `REJECTED`/`SUPERSEDED` mirrors `BlueprintClaim.ClaimStatus` exactly (this codebase's own precedent for a claim-like row with an explicit human decision plus version-driven invalidation), and an explicit accept/reject action-pair matches the Blueprint's confirm/reject convention (`KLAROS_FINAL_API_ARCHITECTURE.md`: "explicit action endpoints, never a generic PATCH").

Naming: class `Recommendation` / table `recommendations`, deliberately **not** reusing `app/models/morning_brief.py`'s existing `MorningBriefRecommendation` / `RecommendationStatus` / `Permission.EXECUTE_RECOMMENDATION` — a different, already-shipped concept (morning-brief action suggestions with execute semantics) this phase must never touch or be confused with. Verified no naming collision: `app/models/recommendation.py` defines its own `RecommendationStatus`/`RecommendationType`/`RecommendationSource`/`RecommendationRunStatus` enums in a separate module; Python's per-module namespacing means there is no import collision, but call sites always import from `app.models.recommendation`, never `app.models.morning_brief`, for this phase's types.

`RecommendationSource` is `BASELINE_RULE` / `VERTICAL_EXTENSION_RULE` only — deliberately excludes a bare `AI` value, since AI is never the source of the *structural* decision in this implementation (see "AI architecture" below).

## Capability model

No hardcoded capability enum was added. Capability keys are free-form strings sourced entirely from two existing/extended registries:

1. The Business Blueprint's own `REQUIRED_CAPABILITIES` section — a business's **confirmed** `BlueprintClaim` rows under that section already hold a list of capability-key strings (this is literal, pre-existing Phase 2 data — see `tests/test_cross_vertical_blueprint_validation.py`'s own `_MEDICAL_TOURISM_CLAIMS`/`_DROPSHIPPING_CLAIMS` fixtures, which already store capability lists like `["multi_currency_commission", "patient_lead_pipeline", "provider_directory"]`). This phase reads them, never re-derives them.
2. Every `VerticalExtension` the organization has enabled (via `OrganizationVerticalExtension`, looked up through `VerticalExtensionService.list_enabled_for_organization` — the exact "plugin function per `VerticalExtension`, looked up by id" mechanism `app/models/vertical_extension.py`'s own module docstring calls for and notes had no real caller until this phase). Each vertical's own `capabilities` registry list contributes *candidate* (non-mandatory) capability keys.

The two lists are merged (deduplicated, case-insensitive) with confirmed-blueprint-claim capabilities marked `required=True` and vertical-menu capabilities `required=False`. No third source and no vertical-name branch exists anywhere in this logic.

## Provider matching (integrations)

The existing, tenant-independent `IntegrationProviderCatalog` (Phase 1) was extended with one additive column, `capabilities: JSON list` (migration `0044`, `app/models/integration_catalog.py`) — the smallest possible extension for deterministic capability→provider matching, explicitly *not* a new `Capability` table (the codebase has no such table and this phase does not add one). Seed data (`app/data/integration_provider_catalog_seed.py`) was tagged with generic capability keys per provider (e.g. `stripe` → `["payment_processing", "billing"]`, `google_calendar` → `["appointment_scheduling", "scheduling", "calendar_sync"]`), and migration `0044` backfills these tags onto any already-seeded rows.

For each capability requirement, `RecommendationService` queries the full live catalog once per run and filters by `capability_key in provider.capabilities` — a plain membership check, no fuzzy logic, no AI. Every matching provider's `implementation_status` (REAL/STUB/WEBHOOK_NORMALIZER) is copied **verbatim** into `Recommendation.provider_implementation_status` and never re-derived or overridden — proven by `test_stub_provider_status_preserved_never_implied_ready` and `test_webhook_normalizer_provider_status_preserved`. Multiple matching providers for the same capability populate each other's `alternatives` list.

## Tool matching

Tool candidates come from the existing, read-only Tool Catalog (`app/services/tool_catalog_service.py::list_tool_catalog`, itself a read-through projection over the live `ToolRegistry` — never `ToolRegistry.execute()`/`.get()` with mutating intent). `RecommendationService` calls `list_tool_catalog` exactly once per generation run (not once per capability — avoiding the "repeated full ToolRegistry scans" performance pitfall called out in this task's brief) and matches each capability_key against each tool's `name`/`description` using simple, generic, deterministic keyword-token overlap (both sides tokenized on `_`/`-`/`/`/whitespace, tokens ≥4 chars, a small universal English stopword list). This is not a per-capability or per-vertical hand-built mapping — it is one generic string-matching function, proven to correctly surface a real registered tool (`crm.create_appointment`) for the `appointment_scheduling` capability in `test_tool_recommendation_matches_real_registered_tool`, and every matched `tool_name` is verified to exist in the live registry (`tool_registry.get(name)`) before the test considers it valid.

## Evidence / provenance

`Recommendation.based_on` is a structured JSON list — each entry identifies its source concretely (`{"kind": "blueprint_claim", "claim_id": ..., "section_key": ...}`, `{"kind": "vertical_extension", "vertical_key": ...}`, `{"kind": "integration_provider_catalog", "provider_key": ...}`, `{"kind": "tool_catalog", "tool_name": ...}`) — never an opaque prose blob. `why`/`what` are separate, human-readable fields built from a deterministic template referencing the same evidence, satisfying the WHAT/WHY/BASED-ON-WHAT rendering contract `KLAROS_FINAL_TESTING_ARCHITECTURE.md` calls for. A recommendation derived from an `AI_INFERRED`-provenance `BlueprintClaim` is never presented as more certain than the claim itself — `confidence` for a `BASELINE_RULE` (claim-derived) recommendation is taken directly from `BlueprintClaim.confidence` when present (falling back to 0.95 only for claims with no stored confidence, i.e. `FACT`/`USER_STATED`-shaped claims), and a `VERTICAL_EXTENSION_RULE` (registry-menu-derived, `required=False`) recommendation is capped at a flat, deliberately-lower 0.6 to reflect it is a candidate, not a stated fact.

## AI architecture — not used, and why

`KLAROS_MASTER_IMPLEMENTATION_ROADMAP.md`'s Phase 4 section permits AI only for the `why`/`what` *narrative* text, and explicitly forbids it for the structural "what to recommend" decision. Auditing every step of this pipeline (capability collection, provider matching, tool matching) found each one fully answered by structured registry/claim data the business itself confirmed or the platform already curated — there was no genuine semantic-reasoning gap for an LLM to fill anywhere, including for the `why`/`what` text, which a deterministic template renders directly from the same evidence a human or a future UI can already see. This implementation therefore does not call `AIProvider`/`generate_structured()`/`record_ai_invocation()` at all. This is a deliberate scope decision, not an oversight: **prefer deterministic matching wherever structured metadata already answers the question** (this task's own instruction) was satisfied at every step, so introducing an AI call anywhere would have added hallucination surface, a second execution path, and nondeterminism with zero corresponding benefit. Because the pipeline is 100% deterministic, "hallucinated provider/tool/capability/vertical" is structurally impossible — every `provider_key` comes from a live `SELECT` against `IntegrationProviderCatalog`, every `tool_name` from the live `ToolRegistry` projection, and every `capability_key` from a `BlueprintClaim` the business itself confirmed or a `VerticalExtension` row the platform curated. No separate "hallucination-guard validation" step was needed as a result; if a future phase adds an AI-assisted narrative pass, the guard-rail architecture this phase leaves in place (query-real-registry-before-persist, one `Recommendation` model shared by every source) is exactly what such a pass would validate against.

## Recommendation lifecycle

`PROPOSED` (initial) → `ACCEPTED` | `REJECTED` (exactly one, explicit action endpoint each, idempotent on repeat, mutually exclusive — accepting a rejected recommendation or rejecting an accepted one is a 409) → `SUPERSEDED` (automatic, only ever applied to a still-`PROPOSED` row left over from an older blueprint version when a new run executes; `ACCEPTED`/`REJECTED` rows are never touched by a later run — a human decision is not retroactively erased). Accept/reject never themselves connect a provider, execute a tool, send a message, or create an agent — proven by `test_accept_never_executes_a_tool_or_creates_a_connection`.

## Blueprint version binding

Every `Recommendation` snapshots the exact `blueprint_id`/`blueprint_version` it was generated against. A `RecommendationRun` envelope records the same binding plus which verticals were considered and how many recommendations resulted (`KLAROS_FINAL_DOMAIN_MODEL.md`/this task's explicit "RecommendationRun-shaped concept" instruction). Generating a new run for a tenant supersedes every still-`PROPOSED` recommendation left over from an older blueprint for that tenant. Proven end-to-end by `test_blueprint_version_binding_supersedes_prior_run` (Blueprint v1 → Run A → edit → Blueprint v2 → Run B → Run A's recommendation is `SUPERSEDED`, Run B's is current) and `test_accepted_recommendation_survives_a_new_run`.

Every `RecommendationService` method takes an explicit `tenant_id` and filters every query by it, mirroring `BusinessBlueprintService` exactly. ## Database

New tables: `recommendation_runs` (`blueprint_id` FK, `blueprint_version`, `status`, `triggered_by`, `verticals_considered` JSON, `recommendation_count`, `completed_at`), `recommendations` (`run_id`/`blueprint_id` FKs, `blueprint_version`, `type`, `capability_key`, `provider_key`, `provider_implementation_status`, `tool_name`, `what`, `why`, `based_on`/`dependencies`/`cost_estimate`/`alternatives` JSON, `required` bool, `confidence` float with a `CHECK (confidence BETWEEN 0 AND 1)` constraint, `source`, `source_vertical_key`, `status`, `decided_by`/`decided_at`/`rejection_reason`). One additive column on the existing `integration_provider_catalog`: `capabilities` JSON list. Migration `alembic/versions/0044_recommendation_engine.py`, `down_revision="0043"`.

Indexes: FK indexes on every FK column; `(tenant_id, blueprint_id)` on both new tables; `(tenant_id, blueprint_id, status)` and `(tenant_id, run_id)` on `recommendations`; a **duplicate-prevention** unique index on `(run_id, type, capability_key, COALESCE(provider_key,''), COALESCE(tool_name,''))` — an expression index, not a plain multi-column one, specifically because a plain unique index does not catch two `CAPABILITY` rows (both `provider_key`/`tool_name` NULL) for the same run+capability under standard SQL NULL-uniqueness semantics; this was caught only by the real-Postgres test, not SQLite, and fixed before landing (see "PostgreSQL" below).

## PostgreSQL validation

Real instance: pgserver-provisioned PostgreSQL 16, database `klaros`, socket `/private/tmp/klaros_pg1`, role `postgres` (pre-existing on this host, at head `0043`; Docker unavailable). `alembic upgrade head` (0043→0044) succeeded. Two full downgrade(`0043`)/upgrade(head) cycles run for determinism — both clean, `alembic current` ends at `0044 (head)` both times. Real bugs caught only against Postgres and fixed before landing:

1. **Insert-ordering**: `RecommendationRun`/`Recommendation` rows were both `session.add()`-ed in one flush with no ORM `relationship()` configured between them; SQLite (no FK enforcement by default) silently accepted any order, but real Postgres raised `ForeignKeyViolationError`. Fixed with an explicit `await session.flush()` after adding the run, before adding its recommendation rows.
2. **NULL-uniqueness gap**: the duplicate-prevention unique index, as a plain multi-column index, did not reject two `CAPABILITY` rows (both `provider_key`/`tool_name` NULL) for the same run+capability, since standard SQL treats NULL as distinct-from-itself in unique indexes. Fixed with a `COALESCE(..., '')`-based expression unique index (model `__table_args__` + migration, PostgreSQL path; SQLite path in the migration keeps the plain index, since SQLite's `Base.metadata.create_all()` test path uses the ORM-declared expression index directly, not the migration).

RLS verified: `relrowsecurity=true`, `relforcerowsecurity=false`, exactly 1 `USING(true)` policy per table, on both new tables. `CHECK (confidence BETWEEN 0 AND 1)` and the duplicate-prevention unique index both verified to raise real `IntegrityError`s at the DB level (not just app logic). The full pipeline test (activate blueprint → generate → list → constraint checks) passed against this real instance.

## Known limitations

- Tool matching uses simple deterministic keyword-token overlap, not a curated per-capability tool map — it will miss a genuinely relevant tool whose name/description shares no token with the capability key, and could in principle over-match on a coincidental shared word (mitigated by requiring ≥4-character tokens and excluding common stopwords, and capped at 3 matches per capability).
- `IntegrationProviderCatalog.capabilities` tags were authored by this implementation (a judgment call, since no such field/data existed before Phase 3) rather than sourced from an existing verified-against-reality list the way `implementation_status` was in Phase 1 — they are reasonable, conservative tags matching each provider's own `category`/`description`, but not independently re-verified against each adapter's actual capability surface the way `EXPECTED_REAL`/`EXPECTED_STUB` were.
- No AI-assisted narrative generation exists yet (a deliberate scope decision — see "AI architecture" above), so `why`/`what` text is template-generated, not naturally-worded prose. A future phase could add this behind the same guard-rail shape this phase established, without changing the model.
- `cost_estimate` is always `null` in this implementation — no cost-estimation data source exists yet in the registries this phase reads from; the column exists (per the 8-field contract) but is never populated.
