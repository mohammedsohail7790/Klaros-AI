## Data model validation

`PatientLead extends Lead` (not a fork) — confirmed viable because `Lead.service_requested`/`description`/`location` are free-text fields already capable of carrying procedure/geography detail before the structured `PatientLead` extension even exists, meaning even a Phase-2-only deployment (Discovery/Blueprint live, domain extension not yet built) produces a usable, if less structured, medical-tourism lead flow — a genuine incremental-value property of the extension pattern, not just a theoretical one.

`ReferralCommission extends Referral` — confirmed necessary because the current `Referral`/`ReferralReward` model has no currency field (verified `retention.py:273-325`) and its own docstring states issuance "is an internal record only," so cross-border, real-money commission tracking genuinely requires the extension, not just configuration of the existing model.

## What existing code required zero change

`Lead`, `Customer`, `Appointment`, `LeadService`, `public_leads.py`, `Stripe` client, RBAC/permission chain, `ToolRegistry`, `AuditLog` — all reused exactly as-is, per the extension pattern's design goal (`KLAROS_DOMAIN_EXTENSIBILITY_SPEC.md` §2, rule 2).
