## 3. Reconciliation decisions

1. **`Organization.autonomy_level` is untouched.** Not read, not written to, not resurrected anywhere in Phase 4 code. Autonomy is enforced entirely at the new `Agent.autonomy_tier` level, per `KLAROS_FINAL_SECURITY_MODEL.md §B`'s explicit replacement-architecture instruction.
2. **No second execution engine.** `ToolRegistry.execute()` was extended in place with two new pre-checks (`_check_agent_tool_permission`, `_check_agent_autonomy`), exactly as `KLAROS_FINAL_AGENT_MODEL.md`'s "What must change, precisely" section specifies — inserted before the existing RBAC check, never reordering or replacing any of the existing 9 steps. `ActorType.AGENT` was added as an additive `StrEnum` value (confirmed via source read that every actor-type-bearing column in this codebase is a plain `String`, not a native Postgres enum type — so no migration was needed for this specific addition, matching the doc's own stated verification). `AgentExecutionService` sits above `ToolRegistry`/`AIExecutionService` exactly as prescribed — it decides *which* tool to call (in this phase, that decision is made by the human caller via the API request body, not by an LLM — see §9 "No general autonomous loop yet" below) and hands the request to `ToolRegistry.execute()` unchanged.
3. **`AgentToolPermission` vs. `AgentVersion.tool_permissions_snapshot`.** `KLAROS_FINAL_AGENT_MODEL.md` describes both a live join table (`agent_id`, `tool_name`, optional `constraint`) *and* a denormalized snapshot on `AgentVersion` "for reproducibility even if permissions later change" — the doc does not spell out which one execution-time checks actually consult. Resolved explicitly: `AgentToolPermission` is the **live, mutable, deny-by-default** grant table an operator edits before publishing a version; `AgentVersion.tool_permissions_snapshot` is captured at version-creation time and **re-captured one final time at publish time**, and it is this **immutable snapshot on the agent's current PUBLISHED version** — never the live table — that `ToolRegistry._check_agent_tool_permission` actually authorizes against. This is what makes Version Immutability hold: granting or revoking a live `AgentToolPermission` row after a version is published can never change what that already-published version is authorized to do.
4. **Autonomy tier per-tier enforcement semantics.** Neither source document specifies exact per-tier mechanics beyond naming the four tiers (Observe/Recommend/Execute-with-approval/Execute-autonomous) and the composition rule ("can only narrow, never widen"). This implementation's own explicit, documented, and tested policy (see `app/models/agent.py::AgentAutonomyTier`'s docstring):
   - `OBSERVE` / `RECOMMEND` → ceiling = `BLOCKED` (no tool execution permitted through this agent at all in this phase; the two tiers remain distinct in the enum for a future recommendation-only-output phase, but enforce identically today, since no such output path exists yet).
   - `EXECUTE_WITH_APPROVAL` → ceiling = `APPROVAL_REQUIRED` (every tool call is forced through a human approval, regardless of the tool's own possibly-`AUTO` policy).
   - `EXECUTE_AUTONOMOUS` → ceiling = `AUTO` (pure pass-through to the tool's own resolved `ActionPolicy` — never bypasses a tool's own `APPROVAL_REQUIRED`/`BLOCKED`, `SYSTEM_BLOCKED_TOOLS`, or the `ai_paused` kill switch).
   - Composition: `final_policy = stricter(tool's own resolved ActionPolicy, tier ceiling)`, strictness order `AUTO < APPROVAL_REQUIRED < BLOCKED` — implemented in `ToolRegistry.execute()` right after `PolicyService.resolve()`, before the `BLOCKED`/`APPROVAL_REQUIRED` branches.
5. **Agent actor needs a `Role` for the existing (unchanged) RBAC check inside `ToolRegistry.execute()`.** Neither doc addresses this. Resolved by adding `Agent.acting_role`, set from the creator's own `Role` at creation time (never client-escalatable, editable only while the agent is `DRAFT`) and carried into the `ExecutionContext.role` field for every execution — the existing `role_has_permission` check therefore still runs, unmodified, for every Agent-initiated tool call.
6. **`AgentExecution.status` enum.** `KLAROS_FINAL_AGENT_MODEL.md` names `RUNNING/COMPLETED/FAILED/HALTED`. This implementation adds `PENDING` (row created, governance checks in flight) and `WAITING_APPROVAL` (parked on an `ApprovalRequest`) as additive, reconciled states — needed to make the Approval Integration requirement concretely testable and observable via the API. A rejected approval transitions the execution to `HALTED` (never attempted), while an approved-but-failing tool call transitions it to `FAILED` (attempted and erred) — a deliberate distinction.
7. **Approval integration requires threading agent identity through `ApprovalRequest`.** Neither doc mentions this explicitly, but it is a direct consequence of "the existing approval system reused, unbypassable, auditable": `ApprovalRequest` gained three new nullable columns (`agent_id`, `agent_version_id`, `agent_execution_id`) so `ApprovalExecutionService._reconstruct_context` can rebuild the exact governed `ExecutionContext` an Agent-initiated call needs on resume, and so a rejected/executed outcome can update the originating `AgentExecution` row without a second lookup mechanism. **A real bug was caught here against real Postgres** (see §9) — `ApprovalExecutionService`'s pre-existing `_detached_copy` helper is a curated field-by-field copy function that predates these three columns and silently dropped them, causing every Agent-initiated approval resume to fail with "missing agent identity". Fixed by adding the three fields to `_detached_copy`; both affected tests (`test_approved_execution_resumes_and_completes`, `test_repeated_approval_callback_does_not_duplicate_side_effect`) now pass.
8. **Recommendation → Agent boundary.** Per this phase's explicit instruction, no automatic Agent-creation-from-Recommendation helper was built — `Agent.source_blueprint_id`/`source_blueprint_version`/`source_recommendation_id` are historical-traceability-only nullable columns an operator can optionally populate when manually creating an Agent via the API; nothing in `RecommendationService` or the recommendation-accept endpoint creates or touches an `Agent`.
9. **No autonomous loop.** Verified this is correct scope: `AgentExecutionService.run_action` executes exactly one caller-declared tool call per invocation. `AgentVersion.max_tool_chain_depth` is modeled (for a later phase) but not enforced as a loop boundary here, since no loop exists yet to bound.

## 4. Agent model (`backend/app/models/agent.py`)

`Agent` (tenant-scoped): `id`, `name`, `purpose`, `status` (`AgentStatus`: DRAFT/ACTIVE/PAUSED/ARCHIVED), `autonomy_tier` (`AgentAutonomyTier`), `acting_role`, `current_version_id` (circular FK to `agent_versions`, added post-table-creation via `use_alter=True` / a guarded `op.create_foreign_key` in the migration), `source_blueprint_id`/`source_blueprint_version`/`source_recommendation_id` (historical traceability only), `created_by`.

Lifecycle transition table (`app/services/agent_service.py::_VALID_TRANSITIONS`): `DRAFT → {ACTIVE, ARCHIVED}`, `ACTIVE → {PAUSED, ARCHIVED}`, `PAUSED → {ACTIVE, ARCHIVED}`, `ARCHIVED → {}` (terminal). Activating requires `current_version_id` to be set (i.e., at least one published version). Editing an agent's own `name`/`purpose`/`autonomy_tier` directly is only permitted while `DRAFT`.

## 5. Agent version model

`AgentVersion` (tenant-scoped, immutable once `PUBLISHED`): `agent_id`, `version` (unique per agent), `status` (DRAFT/PUBLISHED/DEPRECATED), `instructions_snapshot`, `tool_permissions_snapshot` (JSON list of `{tool_name, constraint}`, captured at creation and re-captured at publish), `memory_refs`, `triggers`, `max_executions_per_hour`, `max_concurrent_executions`, `max_tool_chain_depth`, `approval_policy_override`, `created_by`, `first_executed_at`. Publishing a new version automatically deprecates the agent's prior `PUBLISHED` version and updates `Agent.current_version_id`. No update path exists for a `PUBLISHED`/`DEPRECATED` version's executable columns anywhere in `AgentService` — a re-publish attempt on an already-published version raises `AgentVersionImmutableError`.

## 6. Tool permission model

`AgentToolPermission` (tenant-scoped, live/mutable): `agent_id`, `tool_name`, `constraint_config`, unique on `(agent_id, tool_name)`. Every grant is validated against the live `ToolRegistry` at grant time (`tool_registry.get(tool_name)`) — an unknown tool name raises `UnknownToolError` and is never persisted. Deny-by-default: an agent with zero grants has zero authorized tools. Execution-time authorization reads the immutable `AgentVersion.tool_permissions_snapshot` of the agent's current version, not this live table (see reconciliation §3.3).

## 7. Execution model

`AgentExecution` (tenant-scoped): `agent_id`, `agent_version_id`, `trigger_source` (MANUAL/SCHEDULED/EVENT — only MANUAL is reachable in this phase), `triggered_by`, `status` (`AgentExecutionStatus`: PENDING/RUNNING/WAITING_APPROVAL/COMPLETED/FAILED/HALTED), `tool_name`, `tool_input_summary` (redacted via the existing `app/tools/redact.py::redact_input`), `result_summary`, `error_message`, `approval_request_id`, `idempotency_key` (unique per `tenant_id`+`agent_id`, NULLs distinct), `correlation_id`, `started_at`/`completed_at`.

## 8. Autonomy — exact policy (see reconciliation §3.4 for the full table)

Implemented in two places, composed, never duplicated:
- `ToolRegistry._check_agent_autonomy` (`app/tools/registry.py`) computes the tier's `ActionPolicy` ceiling.
- `ToolRegistry.execute()`'s existing policy-resolution block composes `stricter(tool_policy, tier_ceiling)` before the existing `BLOCKED`/`APPROVAL_REQUIRED` branches — the tier can only narrow.

Tested for real behavior (not just enum existence) in `tests/test_agent_execution_service.py`: `test_observe_tier_never_executes`, `test_recommend_tier_never_executes`, `test_execute_with_approval_tier_forces_approval_even_for_auto_tool`, `test_execute_autonomous_tier_runs_auto_tool_without_approval`.

## 9. Approval integration — exact behavior

Reuses `ApprovalRequest`/`ApprovalExecutionService` entirely unchanged in mechanism — only additive nullable columns were added (see reconciliation §3.7). When `ToolRegistry.execute()` resolves `APPROVAL_REQUIRED` for an Agent-initiated call, it raises `ToolApprovalRequiredError` exactly as it always has; `AgentExecutionService.run_action` catches it and transitions the `AgentExecution` to `WAITING_APPROVAL`. A human's `POST /approvals/{id}/approve` (existing, unchanged endpoint) resumes execution through `ApprovalExecutionService.execute_approved` → `ToolRegistry.execute(..., skip_approval_gate=True)` — the **same governed choke point**, not a second path — and `_record_execution_outcome` updates the originating `AgentExecution` to `COMPLETED`/`FAILED`. A rejection transitions the `AgentExecution` to `HALTED`. The pre-existing `execution_status` compare-and-swap in `ApprovalExecutionService.execute_approved` (unchanged) guarantees a repeated resume callback is a no-op — proven in `test_repeated_approval_callback_does_not_duplicate_side_effect`.

**Real bug caught and fixed against Postgres:** `ApprovalExecutionService._detached_copy` did not carry the three new Phase 4 columns, so every resumed Agent-initiated call failed with "Agent-actor tool call missing agent identity" until fixed (see reconciliation §3.7). This is the "real bug expected against Postgres" this phase's instructions anticipated.

## 16. Known limitations

- `AgentExecutionService.run_action` executes exactly one caller-specified tool call per request — there is no LLM-driven tool selection ("which tool to call" is decided by the human caller via the API request body, not by an AI provider call). This matches this phase's explicit "No general autonomous loop yet" scope boundary, but means the Agent Runtime today is a governed single-action executor, not yet an agent that reasons about which tool to use.
- `AgentTriggerSource.SCHEDULED`/`EVENT` are modeled but nothing creates them — only `MANUAL` (via `POST /agents/{id}/execute`) is reachable. Wiring a scheduler or event-bus subscription is deferred (see §17).
- `AgentVersion.max_tool_chain_depth` is stored but not enforced as a loop boundary, since no multi-step chain exists yet to bound.
- `AgentToolPermission.constraint_config` (e.g., a read-only subset constraint) is stored and snapshotted but not yet interpreted/enforced at execution time — no tool in the existing registry currently defines a constrainable sub-scope, so there was nothing concrete to enforce against in this phase.
- `Agent.acting_role` is fixed at creation from the creator's role; there is no separate "effective role" reconciliation if the creating user's own role later changes — matches this phase's "avoid premature complexity" instruction, flagged honestly rather than silently glossed over.
- No UI was built (this phase's instructions were backend-only Phase 4 scope).
