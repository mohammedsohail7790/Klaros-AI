## B. `Organization.autonomy_level` — final disposition

Re-verified independently three times across this review (see KLAROS_ARCHITECTURE_REVIEW.md §5): defined at `backend/app/models/organization.py:29-31`, defaulted, never updated by any code path, never read by any policy/tool/service logic. The codebase's own comment (`organization.py:66`) already calls it "unenforced/decorative."

**Decision:** deprecate as an enforcement mechanism; keep the column as a UX-only compatibility field (e.g., pre-fills a suggested default tier when a user first creates an Agent in onboarding — display-only, never read by `ToolRegistry` or any policy code). **No migration required now** — no code depends on its value, so nothing breaks by simply ceasing to write meaningful values to it (it can keep defaulting to `LEVEL_0`). **A migration is required later, and only later**, if/when the field is physically dropped — which should not happen until the new Agent autonomy tier model (below) has been live in production for at least one full release cycle, confirmed via KLAROS_MIGRATION_STRATEGY.md's compatibility-layer-first approach, to avoid a big-bang removal of a field some external reporting/UI might still reference.

**Replacement architecture:** autonomy is enforced at the **Agent** level (four tiers — Observe/Recommend/Execute-with-approval/Execute-autonomous), composed with the existing tool-level `ActionPolicy` and the existing `Organization.ai_paused` kill-switch, never replacing either. Full mechanics in KLAROS_FINAL_AGENT_MODEL.md.

## D. Multi-tenancy — current state and RLS introduction plan

### Current state, verified
- `TenantScopedMixin` (`backend/app/db/base.py:25-27`) is **column-definition-only**:
  ```python
  class TenantScopedMixin(UUIDPrimaryKeyMixin, TimestampMixin):
      tenant_id: Mapped[uuid.UUID] = mapped_column(Uuid(as_uuid=True), nullable=False, index=True)
  ```
  It adds a `tenant_id` column and an index. It performs **no automatic query scoping**. `get_tenant_db()` (`deps.py:56-65`) returns the plain, unscoped `db` session — its own docstring states tenant isolation happens at the query layer, by convention, in every repository/service method.
- Verified-by-sampling manual convention: `app/tools/builtin/crm_tools.py` lines 260-261, 449-450, 507, 541, 586 (`select(Lead).where(Lead.tenant_id == context.tenant_id)`, etc.); `app/api/v1/integrations.py` lines 91/103/120/133 (passes `current_user.tenant_id` explicitly into service methods, which then filter). This is a **manual, disciplined, but unenforced convention** — not a mechanism. A single missed `.where()` clause in any new endpoint or service method is a cross-tenant data leak with no second layer to catch it.
- Background jobs / Temporal workflows: workflow inputs carry `tenant_id` explicitly (verified in `app/workflows/activities.py`), but this is again convention, not an enforced boundary — a workflow activity that forgets to filter would not be caught by anything at the data layer.
- Redis: tenant-key-namespacing convention **not independently re-verified in this pass** — carried forward as **UNKNOWN — REQUIRES VERIFICATION** from KLAROS_SECURITY_EVOLUTION_PLAN.md, since Redis Streams is used for both the event-bus transport and rate limiting, and neither was traced key-by-key in this review.
- Event bus: events are written to Postgres with `tenant_id` (durability-first design, `app/events/bus.py`) — the event table itself is tenant-scoped-by-convention like everything else; RLS should cover it in the same rollout.
- Integrations, knowledge/RAG, voice: all confirmed to carry `tenant_id` on their respective tables (`IntegrationConnection`, `KnowledgeFile`/`KnowledgeChunk`, voice call/session tables), same manual-convention caveat applies uniformly.
- Object storage: no object-storage layer is live yet (`OBJECT_STORAGE_ENDPOINT` documented as not-yet-implemented in `.env.example`) — tenant-scoping design for it is deferred to when it's actually built (KLAROS_FINAL_DEPLOYMENT_ARCHITECTURE.md), not retrofitted here speculatively.
- Public endpoints: `public_leads`, `public_quotes`, `public_contracts`, `public_invites`, `webhooks`, `marketplace_webhooks`, `voice_stream` are the confirmed non-JWT-auth surface — these resolve tenant from a signed/opaque token or webhook payload, not from a session; RLS session-variable setting (below) must have an explicit code path for these that sets the tenant context from that resolved value, not from `CurrentUser`.

### RLS introduction plan (concrete, not "just add RLS")

**Which tables, in order (smallest-blast-radius-first, matching KLAROS_SECURITY_EVOLUTION_PLAN.md's phase design, re-affirmed here):**
1. **Phase 0 (Instrumentation, no behavior change):** enable RLS in **permissive/audit mode** — a policy that always evaluates true but logs (or, in Postgres terms, is paired with an application-level shadow-check) on the 3-5 highest-sensitivity existing tables first: `IntegrationConnection` (credentials), `ApprovalRequest`, `AuditLog`, `CompanyMemory`, `Organization`/`User`. Goal: prove the session-variable plumbing works and collect evidence of whether any existing query path would have failed a real tenant check, with zero risk of breaking production.
2. **Phase 0/1 (Permissive-with-bypass):** `FORCE ROW LEVEL SECURITY` with a policy `USING (tenant_id = current_setting('app.tenant_id')::uuid)`, but a `BYPASSRLS`-equivalent explicit escape hatch for the service/migration role only (`app_migrator`), so schema changes and legitimate cross-tenant admin queries (support tooling) are not silently broken. Roll out table-by-table, smallest-blast-radius-first, in the same sensitivity order as step 1, moving down the full ~190-table list confirmed to carry `TenantScopedMixin`.
3. **Phase 1+ (Remove bypass by sensitivity):** for tables above a defined sensitivity threshold, remove the general bypass; only the narrowly-scoped migration role retains it, and only for actual DDL/migration windows.
4. **New tables (Blueprint, Agent, Recommendation, Website, domain-vertical tables — all of KLAROS_FINAL_DOMAIN_MODEL.md): RLS-on-day-one.** No new table ships without its policy in the same migration that creates it — this is the concrete difference between this plan and "add RLS someday": new work is never allowed to add to the unenforced-convention pile.

**How tenant context reaches Postgres:** the FastAPI request-scoped DB session (`get_db()`, `app/db/session.py:53-55`) issues `SET LOCAL app.tenant_id = '<uuid>'` as the first statement of every transaction, sourced from `CurrentUser.tenant_id` (JWT-derived) for authenticated requests, or from the resolved tenant on the public/webhook code paths named above. `SET LOCAL` scopes the setting to the current transaction only, so it cannot leak across pooled-connection reuse between requests — this is the specific mechanism that makes connection pooling safe with RLS, and must be verified with a dedicated test (see KLAROS_FINAL_TESTING_ARCHITECTURE.md) before Phase 0 is considered complete, since a `SET` (non-`LOCAL`) mistake would be a severe, silent cross-request leak.

**Transaction/session implications:** every service method must run inside a transaction that has had `SET LOCAL` issued — a raw `session.execute()` outside the standard `get_db()` dependency (if any exist) is a bypass risk and must be audited for during Phase 0 (see KLAROS_PHASE_0_IMPLEMENTATION_PLAN.md acceptance criteria).

**Service-account / background-worker behavior:** the Temporal worker and event-worker processes do not have a per-request `CurrentUser` — each activity/handler must explicitly set `app.tenant_id` from the `tenant_id` already carried in its workflow input/event payload (verified present) before touching the DB. This is new code, not automatic, and is a named Phase 0 task.

**Admin access:** a genuine cross-tenant admin/support query path (if one is ever needed) must use the explicit, audited `app_migrator`-equivalent bypass role, never a silently-permissive policy — and every use of that role should itself be logged.

**Migrations:** RLS policies are added in the same Alembic migration as any schema change to a table reaching Phase 0/1 rollout; migrations themselves run as the bypass-capable role (already true of how Alembic connects today, per `app/db/session.py`/`alembic/env.py` — not independently re-verified line-by-line in this pass, flagged **UNKNOWN — REQUIRES VERIFICATION** for the exact Alembic connection role).

**Testing strategy:** a dedicated cross-tenant isolation test suite (KLAROS_FINAL_TESTING_ARCHITECTURE.md) that, for every RLS-enabled table, attempts a read/write as Tenant A against Tenant B's row and asserts zero rows returned / permission denied — run as a **non-skippable CI gate** for any PR touching a table already on RLS or being newly added.

**Rollback strategy:** RLS policies can be disabled per-table (`ALTER TABLE ... NO FORCE ROW LEVEL SECURITY` / drop policy) without a data migration, since the underlying `tenant_id` column and its manual `.where()` filtering convention remain in place throughout the rollout — RLS is additive defense-in-depth, not a replacement for the existing discipline, so disabling it in an emergency reverts to (already-present) app-layer-only protection rather than to no protection at all.

## S. Security threat model (CRITICAL/HIGH/MEDIUM/LOW)

| Area | Classification | Reasoning |
|---|---|---|
| Tenant isolation (app-layer only, no RLS) | **CRITICAL** | Sole enforcement layer is a manual per-query convention (confirmed, not assumed) across ~190 tenant-scoped models; one missed `.where()` in any current or future endpoint is a silent cross-tenant data leak with no second layer to catch it. Directly actionable via the RLS plan above. |
| Agent autonomy without tier/permission scaffolding | **CRITICAL** | Granting a future Agent Runtime the full 233-tool surface with only prompt-level restriction, before `AgentToolPermission`/tier checks ship, would let a single prompt-injection succeed at anything a human with that agent's nominal role could do. Mitigated by the mandatory ordering in KLAROS_FINAL_AGENT_MODEL.md and the dependency graph gating Agent autonomous-execution behind Phase 0. |
| Credential encryption | **LOW** (as currently implemented) | Fernet-encrypted `IntegrationConnection.encrypted_credential`, boot-time refusal on default/unset key (`main.py:42-46`, `:300-314`), verified via direct code read. Residual risk is key-management/rotation practice, not the encryption mechanism itself — not independently assessed here (out of scope: ops key-custody process). |
| Object/file storage encryption at rest | **UNKNOWN — REQUIRES VERIFICATION** | Object storage is not yet live; when it is (KLAROS_FINAL_DEPLOYMENT_ARCHITECTURE.md), encryption-at-rest must be an explicit acceptance criterion, not assumed from the credential-store precedent. |
| Prompt injection via Agent tool-calling | **HIGH** | Once the Agent Runtime's tool-calling path exists (extending the pattern already proven safe in the voice Realtime path), a malicious document ingested into Knowledge or a crafted customer message could attempt to manipulate an agent into calling a tool outside its intended purpose. Mitigated by: tool-level RBAC/policy (existing), agent-level tool permission allowlist (new), autonomy-tier approval gating for anything risk-tagged (new), and a mandatory prompt-injection test suite gating any tier above Observe (KLAROS_FINAL_TESTING_ARCHITECTURE.md). Not eliminated by any single layer — defense in depth is the actual mitigation, which is why no single layer is allowed to be "the" safety mechanism (explicit rejection of prompt-only safety in `KLAROS_DO_NOT_BUILD_YET.md` §5). |
| Tool abuse / agent escalation (agent exceeding its declared purpose) | **HIGH** | Mitigated by `AgentToolPermission` allowlisting (deny-by-default — an agent has zero tools until explicitly granted) and the hard, tier-independent ceiling that `financial_risk`-tagged tools and `SYSTEM_BLOCKED_TOOLS` are never bypassable regardless of tier. |
| SSRF via integration adapters or website-builder form submission | **MEDIUM** | Integration adapters call fixed, known third-party API hosts (Stripe/QuickBooks/Google) — low SSRF surface today. The Website Builder's public form submission is explicitly restricted to an allowlist of existing/new narrow public endpoints (`public_leads`, `public_appointment-requests`), never arbitrary URLs — this is a designed mitigation, not an incidental one, and must remain enforced at the schema-validation layer (form specs cannot declare an arbitrary `action` URL). |
| Arbitrary code execution via Website Builder or agent-generated workflow steps | **LOW-by-design** | Explicitly and structurally prevented: Website Builder never executes LLM-generated code (fixed component registry, JSON content-slot filling only); Workflow Generation compiles into existing Automation/Temporal definitions, never executes agent-authored source. Classified LOW because the mitigation is architectural exclusion, not a runtime guard that could be bypassed — verified this remains true throughout KLAROS_FINAL_FRONTEND_ARCHITECTURE.md and KLAROS_FINAL_AGENT_MODEL.md's Workflow Generation section. |
| Knowledge ingestion (malicious/poisoned documents) | **MEDIUM** | A tenant's own uploaded documents feed embeddings (`KnowledgeFile`/`KnowledgeChunk`) and, via retrieval, agent context. A poisoned internal document is a prompt-injection vector (see above) but is tenant-scoped by construction — cannot cross tenants — and Company Memory's ACTIVE-only-via-human-confirm gate limits how much a single document can autonomously become "trusted fact." |
| Public endpoints (`public_leads`, `webhooks`, `voice_stream`, etc.) | **MEDIUM** | Non-JWT surface by design; correctly identified as requiring separate, explicit tenant-resolution logic (signed tokens/webhook secrets) rather than `CurrentUser` — audited in this pass as a named RLS-plumbing edge case (§D above), not independently penetration-tested. |
| Rate limiting | **MEDIUM** | `core/rate_limit.py` exists and is used (confirmed present, used by Twilio-related paths per backend research); coverage across all new Agent/Discovery/Recommendation endpoints is not yet verified since those endpoints don't exist yet — must be an explicit Phase 0/1+ requirement for every new route group, not assumed inherited. |
| Audit logs | **LOW** | Real, comprehensive (`AuditLog` on every tool-execution outcome, `AIInvocationLog` for every LLM call) — the strongest-verified subsystem in the whole review. |
| Secrets management | **LOW-MEDIUM** | Boot-time guards against default `JWT_SECRET` and unset encryption key are real and verified; broader secrets-in-CI/deployment-pipeline handling is **UNKNOWN — REQUIRES VERIFICATION** since no CI/deployment pipeline exists yet to assess. |
| Background jobs / Temporal workflows (tenant leakage) | **HIGH**, pending verification | Workflow-ID tenant-leakage risk (could a workflow ID or its associated queue leak cross-tenant information, or could two tenants' workflows collide on ID) is carried forward as **UNKNOWN — REQUIRES VERIFICATION** from the prior security document — not independently re-verified in this pass; flagged HIGH pending that verification because Temporal workflow IDs are visible in the Temporal UI (`temporal-ui` service, confirmed present in `docker-compose.yml`) which itself has no confirmed tenant-scoping of its own. |
| CI/CD absence as a security control gap | **HIGH** | Confirmed: zero CI exists. Every other mitigation above (tenant-isolation tests, prompt-injection tests, RLS regression tests) is only as good as a pipeline that actually runs it on every PR — without CI, all of the above are optional discipline, not enforced gates. Directly addressed in KLAROS_PHASE_0_IMPLEMENTATION_PLAN.md and KLAROS_FINAL_TESTING_ARCHITECTURE.md. |

## Pre-autonomy security gate (carried forward, upheld)

No Agent may exceed the **Recommend** tier until all four hold: (1) tenant-isolation RLS is live (at minimum permissive-with-bypass, §D Phase above) on every table the agent's declared tools can touch; (2) `AgentToolPermission` allowlisting is enforced (deny-by-default); (3) the prompt-injection and hard-limit test suites (KLAROS_FINAL_TESTING_ARCHITECTURE.md) pass in CI; (4) at least one staging dry run of the specific agent's tool set has been observed and reviewed by a human. This gate is the concrete translation of "governance before autonomy" that this whole review is built around.
