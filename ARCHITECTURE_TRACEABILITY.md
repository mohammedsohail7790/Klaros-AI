## Phase 25 — Runtime Consistency: One Authoritative EventBus Boundary

Phase 24's own real-HTTP test surfaced a real (if subtle) architectural inconsistency: `POST /automations/scheduled/dispatch-tick` published its `contract.expired` event onto a *different* EventBus object than the one the test's `client`/`event_bus` fixtures had wired and overridden, forcing the test to reach for the real process-wide singleton directly to observe the result. Phase 25's job was to fix that inconsistency in the application architecture itself, not to keep documenting workarounds around it.

**Root cause** (found by inspection, not guesswork): `app/api/tool_deps.py`'s `get_automation_service()`, `get_morning_brief_service()`, and `get_voice_conversation_service()` — plus six route modules (`public_quotes.py`, `public_contracts.py`, `public_leads.py`, `retention.py`, `exceptions.py`, `ar.py`) — resolved the application's `ToolRegistry`/`EventBus` via **bare Python function calls** to `get_tool_registry()`/`get_event_bus()`/`get_wired_event_bus()` instead of accepting them as FastAPI `Depends(...)`-resolved parameters. `app.dependency_overrides` (what tests use to substitute an isolated EventBus) only intercepts `Depends()` resolution at the ASGI routing layer — it has no effect on a bare call to the underlying function object. In real production this was harmless (there is only one process per deployment, and `app/main.py`'s `lifespan()` eagerly wires the one true singleton at startup before any request is served, so every bare call already resolved the same fully-wired object) — but in tests, which deliberately construct an isolated `EventBus` + `ToolRegistry` pair per test and only override the `Depends()` slots, any code path using a bare call silently escaped that isolation and touched the real, `@lru_cache`d, process-wide singleton instead — which, because the cache persists for the whole pytest process, could also leak wiring state between unrelated tests.

**Fix** (see `app/api/tool_deps.py`'s own module docstring for the full account): every one of those functions now accepts its `ToolRegistry`/`EventBus` as a `Depends(get_tool_registry)`/`Depends(get_wired_event_bus)`-defaulted parameter, so FastAPI threads the *same* resolved instance through the whole dependency graph — and a test's override of `get_tool_registry`/`get_wired_event_bus` now correctly propagates to every downstream consumer, no exceptions. `get_tool_registry()` and `get_wired_event_bus()` themselves remain the two necessary bootstrap roots (breaking the circular dependency between "a ToolRegistry needs a bus to let tools publish" and "a wired bus needs a ToolRegistry to build automation handlers that execute tools") — nothing above them needed a third function; **no second EventBus, scheduler, or application container was introduced**. The two non-request contexts that call these functions outside FastAPI's DI scope — `app/main.py`'s `lifespan()` and `app/events/worker.py`'s standalone-process entrypoint — were updated to pass the bootstrap instances explicitly (`get_automation_service(get_tool_registry())`) rather than relying on the old bare zero-arg form. `EventBus` itself gained `@dataclass(eq=False)` (identity-based hashing) so it can be used as an `lru_cache` key for `get_morning_brief_service`.

**Runtime invariant now held**: HTTP request handlers, scheduled automation dispatch, domain event producers (including the public, unauthenticated quote/contract/lead endpoints), and real HTTP end-to-end tests all resolve the EventBus through the identical `Depends(get_wired_event_bus)` boundary. Tests may still override that boundary intentionally (that's what makes per-test isolation possible) — but production code no longer has any path that silently diverges from it. `app/workflows/activities.py`'s Temporal activities were deliberately left calling the bare `get_event_bus()` — inspected and confirmed correct as-is: they run in a genuinely separate OS process (the Temporal worker, `app/workers/main.py`), only ever *publish* events (never call `process_pending`), and in real production (Redis-backed transport) publishing needs no local handler registration — consumption happens in the dedicated `event-worker` process, which is already correctly wired via `get_wired_event_bus()`. Fixing this would have meant threading a bus through Temporal's own activity-registration mechanism for no behavioral benefit — exactly the over-engineering this phase was told to avoid.

**Duplicate-handler protection** (Step 9): `get_wired_event_bus()` is `@lru_cache`d and is the *only* place `register_automation_handlers`/the other domain-handler registrars are ever called for the real process-wide bus; nothing in the codebase calls `.cache_clear()` on it, so the registration body can only ever run once per process. Verified directly in `backend/tests/test_phase25_eventbus_boundary.py::test_wired_event_bus_is_a_true_singleton_with_one_registration_pass` — calling `get_wired_event_bus()` repeatedly returns the identical object with subscription counts that never grow, and at most one `automation_dispatch` subscription exists per event type.

**Regression coverage**: `backend/tests/test_phase25_eventbus_boundary.py` (new) proves the exact Phase 24 scenario is fixed — `POST /automations/scheduled/dispatch-tick` and the follow-on `contract.expired` EVENT automation, using only the standard `client`/`event_bus`/`tool_registry` fixtures and real HTTP calls, no manual bus access anywhere. `backend/tests/test_end_to_end_business_lifecycle.py` and `backend/tests/test_phase24_automations.py` had their now-unnecessary manual-bus workarounds removed and pass unchanged otherwise. No new AI scenarios, business domains, integrations, or duplicate infrastructure of any kind were introduced — this was a hardening-only phase.

## Phase 29 — Targeted PostgreSQL Sweep Concurrency Verification & Hardening

Phase 28 explicitly flagged two sibling sweeps sharing `ContractService.detect_pending()`'s pre-fix unlocked-read shape — `QuoteService.detect_expired()` and `ARService.detect_overdue()` — as unverified, not as assumed-broken. This phase determined the truth of each with real PostgreSQL execution, not inspection.

**QuoteService.detect_expired()** — race **confirmed real** and fixed. A single-quote concurrency test did not reliably reproduce it against a fast local database (20+ runs at 10-way concurrency, one run at 50-way, all clean) — but a forced-`asyncio.Barrier` diagnostic against the identical query/update shape proved the underlying mechanism races (5/5 workers flagged the same row when made to overlap deliberately), and a larger, more production-representative candidate batch (200 stale quotes, sharing one sweep's SELECT+iterate+flush cost across the batch) reproduced it naturally and reliably (4 of 5 runs, ~1200 duplicate flags across a 200-quote batch) without any artificial synchronization. Root cause identical to Contract's: concurrent transactions can all `SELECT` the same stale quote before any `COMMIT`s, each independently reporting the transition and publishing its own `QUOTE_EXPIRED` event. Fixed with the same `.with_for_update(skip_locked=True)` — verified by reverting the fix and re-running the exact regression test (fails 4/5 runs without it, passes reliably with it restored).

**ARService.detect_overdue()** — a **different, real defect** found: not silent event duplication, but an **unhandled crash**. `CollectionService.schedule_next_action()` does its own check-then-insert (SELECT for an existing `CollectionAction`, INSERT if none found) — structurally the same shape `ExceptionService.create_exception()` already handles safely, but missing the second half of that pattern. Under real concurrency, two callers can both pass the "no existing action" check before either commits; the second's `INSERT` then hits the real, pre-existing `uq_collection_actions_tenant_invoice_type` unique constraint and raises an **unhandled** `IntegrityError` — reproduced reliably with ordinary `asyncio.gather` at 10-way concurrency against a single overdue invoice (no barrier or large batch needed; 3 of 10 concurrent calls failed this way every run). Because the per-invoice downstream loop in `detect_overdue()` has no try/except, this would abort processing of every subsequent invoice in the same sweep batch. Fixed with the identical try/except/rollback/re-fetch shape `create_exception` and `CompanyMemoryService`'s supersession logic already use — the constraint was always correct and doing the real work; the code simply never caught the race it made possible. `ExceptionService.create_exception()` itself was inspected and confirmed **already safe** (same CAS pattern, no fix needed) — its own unique constraint (`uq_exceptions_tenant_type_entity_open`) and IntegrityError handling meant no duplicate `EXCEPTION_CREATED` event was ever possible even before this phase, despite `detect_overdue()`'s own initial SELECT sharing the unlocked-read shape — that initial race is harmless once every downstream consumer is itself CAS-protected, which is why `detect_overdue()`'s own SELECT was deliberately left untouched (smallest fix, not a blanket `skip_locked` everywhere).
